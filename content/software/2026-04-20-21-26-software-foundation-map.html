四层分解

把你原始笔记里的条目重新按“越靠下越基础，越靠上越接近使用场景”的方式组织，避免只记住名字，不知道它们彼此关系。

L1

系统核心层

操作系统真正的地基，负责启动、调度、设备、权限、文件系统与运行时根基。

Kernel glibc / musl systemd X11 / Wayland
L2

基础能力层

网络、压缩、加密、IO、日志、音视频与数据库等“通用底层能力模块”。

curl OpenSSL zlib / zstd SQLite
L3

运行与构建层

把代码变成可执行程序，并能调试、部署、追踪、复现问题的那一整套工具链。

GCC / LLVM CMake GDB Git
L4

场景执行层

AI 推理、本地媒体处理、终端工作流、容器与虚拟化，是底层能力面向具体任务的落点。

ggml FFmpeg / GStreamer tmux QEMU / Docker

工具图谱

这里不是原样堆列表，而是提炼出最有代表性的类别与样本。点下面的标签可以快速筛选。

System Core

系统与运行环境

负责开机、进程、设备、文件系统和最基本的用户态运行基础，属于“没有它就没有后面一切”的层级。

代表：Linux Kernel、glibc、musl、systemd、coreutils、util-linux
Transport

网络与传输

下载、同步、远程登录、DNS、抓包与防火墙都在这里，是服务器和分布式协作的血管系统。

代表：curl、wget、OpenSSH、rsync、iproute2、iptables、tcpdump
Media Runtime

多媒体与渲染

音视频编解码、播放管线、图像处理和 2D/3D 渲染的底层基础，很多播放器、编辑器和浏览器都依赖它们。

代表：FFmpeg、GStreamer、SDL2、PipeWire、ImageMagick、Mesa
Inference Stack

AI 推理与张量运行时

模型格式、算子执行、硬件加速与跨平台推理环境，构成今天本地 AI 生态的基础骨架。

代表：ggml、ONNX Runtime、PyTorch、TensorFlow、cuDNN、OpenVINO
Build Chain

开发、构建与调试

代码要变成程序，要能复现、调试、链接、发布，靠的就是编译器、构建系统与版本控制工具链。

代表：GCC、Clang、LLVM、CMake、Make、GDB、Git、pkg-config
CLI Workflow

终端与窗口工作流

终端不只是输入命令，它本身就是高效工作环境。会话复用、文本编辑、模糊查找和窗口管理都很关键。

代表：tmux、ncurses、Neovim、fzf、Kitty、Alacritty、i3、sway
Storage

存储、压缩与文件系统

压缩库、归档工具、块设备与文件系统构成“数据怎么被保存、移动和恢复”的底层支撑。

代表：zlib、zstd、xz、tar、dd、losetup、ext4、btrfs、zfs
Observe

观测、追踪与性能分析

一旦系统变慢、崩溃或行为异常，真正能追到根上的往往不是 GUI，而是这些偏底层的诊断工具。

代表：strace、ltrace、perf、sar、vmstat、iostat、valgrind
Data Plumbing

文本与数据处理

底层工作常常以流和文本为中心，能快速变换数据、查找文件、过滤日志，就能把大量重复劳动自动化。

代表：sed、awk、grep、ripgrep、fd、jq、yq、find

如何判断一个软件是不是“底层”

你给的几份笔记里，其实已经隐含了一个非常清晰的判断逻辑。我把它提炼成 4 个问题。

1. 它是否被大量上层软件依赖？

如果很多应用、框架或服务都建立在它之上，它更像基础设施，而不是单点应用。

2. 它是否主要提供“能力”而非“界面”？

越偏底层，越常见 CLI、库、协议、运行时、服务进程，而不是重 UI 产品。

3. 它是否靠近系统资源？

调度、内存、设备、网络、文件系统、GPU、音视频编解码，越靠近这些越偏底层。

4. 它是否能跨场景复用？

通用性越强，越可能成为“基础骨架级”工具，比如 OpenSSL、Git、SQLite。

高频核心集合

如果只保留最常出现、最值得优先理解的一批，那么下面这些几乎可以视为“底层基础必修课”。

  • 系统骨架：Kernel、glibc / musl、systemd、coreutils、procps、util-linux
  • 网络骨架：curl、OpenSSH、iproute2、wget、rsync、openssl
  • 开发骨架：git、gcc / clang、cmake、make、gdb
  • 数据骨架：sqlite3、zlib、zstd、tar、jq
  • 媒体骨架：ffmpeg、sdl2、pipewire、libjpeg / libpng
  • AI 骨架：ggml、onnx runtime、cuda / rocm、pytorch

按场景理解组合

比背名字更有效的是，知道不同任务会天然调用哪一层底座。

  • 极简 Linux / 服务器：coreutils、systemd、OpenSSH、curl、rsync、journalctl、tmux
  • 本地 AI 部署：ggml、ONNX Runtime、CUDA / ROCm、Python、OpenSSL、sqlite
  • 多媒体工作站：FFmpeg、GStreamer、SDL2、PipeWire、Mesa、ImageMagick
  • 开发环境：git、gcc / clang、cmake、gdb、ripgrep、fd、jq

一句话总结

你这 4 份内容的本质，不是在列软件，而是在回答一个更底层的问题：

软件世界真正稳定的，不是应用层产品，而是那些安静支撑一切的基础组件。

它们经常没有炫目的界面，却决定了系统是否能启动、程序是否能编译、网络是否能通信、 媒体是否能解码、模型是否能推理。理解这些底层组件，等于理解现代软件工业的基础骨架。
